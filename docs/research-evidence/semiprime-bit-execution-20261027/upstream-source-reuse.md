## 1. Actual packing from arbitrary scopes: strongest immediate reuse

`SqrtLog/PackingCallerProgramModel.lean:12` defines `PackingCallerProgram.Problem` by arbitrary `scopes : List (List Nat)`, n, a prefix mask, and positive r,Q,s. It has no k or maximum-factor-arity parameter. Its proof-only `.spec` is derived from the actual assigned words, and the actual incidence/depth/alphabet/plan identities follow in that same file. An empty mask suffices for our initial network; the general mask interface may also support a later prefix adapter.

`SqrtLog/PackingCallerProgramJoin.lean:16`, `compute_eval`, proves actual `Eval compute ...` from literal source/empty-workspace encoding predicates, a complete ordered word alphabet, and the public parameter store. It returns the computed packing bank/state; the packing value is not an answer supplied by the caller. `PackingProgramAssemblyScope.lean:77`, `Scope.run`, supplies the underlying native-scope selector execution.

`SqrtLog/PackingCallerProgramBoundsPolynomial.lean:77`, `Bounds.coreBudget_polynomial`, gives absolute constants C,d bounding this actual core in `(scalarSize+1)^d`. Crucially `PackingCallerProgramBoundsBasic.lean:13` explicitly defines scalarSize as n+factor count+incidences+r+Q+s+r^Q+r^(2Q)+encoded scopes/mask/parameter lengths+1. There is no hidden 2^n in that size. The `bankOutput_word_polynomial` theorem at :85 bounds retained output words. This is a substantially stronger reusable source-setup resource component than a fixed-k SAT endpoint alone.

Compatibility obligations: serialize our actual ordered scopes and explicit Fin coordinates; prove their entries are within n; use the exact ordered alphabet; reconcile source tolerance with epsilon=1/s (the upstream weights use M/(s*(r^Q)^2) and n/(2r)). Our generic API permits arbitrary rational epsilon, so an adapter must specialize a scheduled reciprocal-integer tolerance or prove an equivalent scaling. Upstream uses integer-score/incremental selection; its word assignment is not definitionally our `FiniteEnumerations.searchWords`. Prove same objective comparisons/tie order after finite reindexing, or build the semantic layout from the upstream-produced words and its own proved packing contract. Merely recognizing the same optimization problem is insufficient.

## 3. Generic opaque-word source expression emitter

`Subexp/UniversalRowSourceProgram.lean:26`, `program_runsIn`, and :52, `primitive_run`, are genuine fixed bit programs from packed scalar/inverse tables and position lists to actual row postfix bytes. They take byte-table validity/readiness and literal encoded scalar words, not a coefficient-polynomial oracle. The output is exactly `rowCode zero one (zero++one) (row tables positions delta limit)`.

`SqrtLog/LayoutProgramSourceTables.lean:14` constructs these tables generically from any encoded scalar type C. `LayoutProgramSourceBounds.lean:25`, `SourceTyped.source_bounds`, proves the actual emitter cost/output-length bounds under fixed scalar width and materialized tables; :45 bounds the native mismatch-index stream. `LayoutProgramSourceNative.lean:21` supplies the actual mismatch scan and :45 the emitter embedding into the source bank. Thus the source syntax/byte assembly need not be reimplemented. However “tables materialized” is a premise at this layer. We still have to supply the finite rational node/inverse/difference constants by actual word arithmetic, pay their creation, pad/encode them to the required common width, and connect source output bytecode with our physical expression interpreter. The pinned numerator/cache programs handle the integer part but do not by themselves materialize all rational inverse tables.

## 4. Generic coefficient semantics versus the specialized physical ring join

`SqrtLog/PolynomialExecutorProgramBasic.lean:24,44` defines the generic expression evaluator and proves `evaluate_correct` for an arbitrary `RepresentedRing C R`; `PolynomialExecutorProgramSource.lean:28,33,53` gives `sourceExpr`, exact `sourceCode_eq` serialization, and `sourceExpr_meaning`. The deeper *machine* assembly is more specialized. `LayoutSourceRowsProgramRowsModel.lean:14`, `sourceRows_relSpec`, and `LayoutSourceRowsProgramModelAssembly.lean:16`, `sourceRows_present_model`, discharge owner traversal and physical polynomial execution, but use `RingModel.Data d`, `SubexpPreparedQuartic.Modulus 3 t`, scalar caches, fixed `Coeff(baseWidth 3 t,d)` words, context readiness, and a concrete source callback contract. The distinction matters: `RepresentedRing` at `SubexpSymbolicCost.lean:548` requires addition/multiplication/negation correctness for EVERY code pair. Our fixed-template rational primitives are exact only under the derived capacity conditions. A finite fixed-width code type cannot globally represent characteristic-zero rational arithmetic under such unconditional operations (its image would contain arbitrarily many integers). Consequently simply declaring our clipped RationalWord backend to be this unconditional fixed-width represented ring would be false. An unbounded valid-word subtype could support a generic rational represented ring, but its machine length/control and bounded-context attachment are a further proof, not an existing consequence of the fixed-width finite-ring source assembly.

## Addendum: the finite-ring alternative is arithmetically viable

`SubexpPreparedQuartic.Modulus 3 t` is **only prepared binary bytes for the integer modulus 3^t**, with length≤baseWidth(3,t)+1 and exact toNat=3^t (`SubexpPreparedQuartic.lean:19`). Its `prepareModulus` actually computes those bytes by repeated binary multiplication and has the explicit quadratic setup bound at :57. It is not an irreducible-polynomial oracle. The separate `RingModel.Data d` contains the actual d ternary coefficients of a monic polynomial irreducible over F3 (`SqrtLog/RingModel.lean:19`). Its ring O_t is `(Z/3^t Z)[X]/(F_t)` using coefficientwise lifts of that polynomial; residue field E is F_(3^d). Physical values are d base words, each base width `baseWidth(3,t)=2t`, with canonical residues modulo 3^t. The "Quartic" namespace does not force d=4 in `RingProgram.modelProgram/modelRing`; their APIs are explicitly arbitrary positive d. Model arithmetic is already an unconditional represented ring with measured setup/budgets.

This is a credible alternative to rational arithmetic, not an arithmetic impossibility. The already-proved `RingModel.Data.decodeCount_natCast` (`RingModel.lean:154`) recovers any ordinary count c<3^t exactly from coefficient zero; `count_eq_zero_iff` also gives exact zero testing in that range. A Boolean n-wire count is≤2^n, so t=n+1 is a simple public sufficient exponent. `RingModelNodes.lean:46,70,76,82` provides Q nonzero residue-distinct lifted nodes when Q<3^d, proving every node and pair difference is a unit. Thus arbitrary Q can be accommodated by d=O(log(Q+1)), with the separate irreducible search/setup paid. The source clearing denominator 2^(R−1) is a unit in this odd-characteristic ring, and Hasse/Taylor coefficients do not inherently require division by factorials. This is the intended reason for the extension, rather than an attempt to invert multiples of 3.

One CANNOT simply reduce our current rational computation modulo 3^t: its nodes 1..Q include nonunits and nonunit differences, and there is no ring map from all of Q into characteristic 3^t. A viable replacement reconstructs the source/interpolation algebra DIRECTLY over O_t at the existing residue-distinct nodes, using the pinned generic unit-based source and finite-ring machine APIs. If instead one globally clears rational denominators containing 3, the known 3-adic valuation must be retained and the modulus enlarged before division/reconstruction; that is extra work, not a free rational-to-ring conversion. Reusing the existing unit-node construction is the cleaner avenue.

The remaining critical join is still real: instantiate those generic finite-ring source/count programs on our actual growing-scope macro-network and its paid local Boolean evaluator, rather than inheriting a fixed-k clause callback or assuming its cost. Relate the finite-ring count to the exact original 0/1 tensor identity, supply all finite-ring setup/input serialization, and prove the growing-scope/streaming/controller cost. The arithmetic does not rule this route out; the verified fixed-k SAT endpoint alone does not close these joins.

### Exact generic count identities versus the CNF-specific endpoint

A readily visible generic semantic endpoint is `GlobalPolynomial.eval_zero_interpolatedGlobalPolynomial` (`GlobalPolynomial.lean:393`). It takes arbitrary finite `Factor.System V E A`, any commutative ring R, an alphabet lift with unit pair differences, and replacement rows restoring coordinates at zero; its CONCLUSION is H(0)=Factor.count as an element of R. There is no CNF or fixed-k assumption. The preceding `eval_zero_eq_factor_count` (:317) even separates an arbitrary exact table-polynomial specification from interpolation. This directly supplies the count equality for arbitrary local Boolean-valued factor tables over O_t once the source/table hypotheses are instantiated.

For the full separated reconstruction algebra, `Counting.explicitRecoveredValue_eq_count` (`Counting.lean:750`) is also generic in a factor system, not CNF. Its alphabet is specifically ZMod p; it assumes the actual lifted layout, unit alphabet differences, residue/kernel/nilpotence and degree data, and derives the reconstructed value equals Factor.count. It does not by itself claim machine runtime. A simple prospective p=3 adapter is to define each original local Boolean checker on ternary inputs by rejecting any input coordinate with value 2 and otherwise invoking the same checker on values 0/1. Original scopes/occurrence bound stay unchanged. Since the actual public graph covers every variable, every accepted ternary assignment is Boolean, so this factor system counts exactly the original Boolean assignments. Local enumeration becomes 3^w rather than 2^w, still 2^O(w), and the rejection scan is linear in scope size. This adapter and its bit execution must actually be proved; interpolation degrees are now up to 2 per variable, so the precise degree/precision guard must be re-instantiated rather than borrowed unchanged.

By contrast, the assembled physical target bridge `SqrtLog/LeafProgramNodeConcreteSharedTarget.lean` (:24–25 and its `query_target_count`) explicitly takes `source : List (List (SAT.Literal ...))` and `hs : q.clauses=...encodedClauses source`. That leaf-query instantiation is CNF-specific. The generic ring, interpolation/count equality, primitive packing, source numerator and byte-emitter components above do not contain that premise. Reusing them could avoid much of the remaining rational machine implementation, but requires the genuine new growing-scope table/decoder/layout-to-program join. It is not legitimate to import the CNF leaf program as though its supplied clause structure were an arbitrary tensor callback.
